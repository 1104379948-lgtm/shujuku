# 自定义表建表指南

> 面向：想在剧情中让 AI 自动维护一张自定义表的用户。

## 一、先分清三条路径

同一张表在不同模式下由不同的链路消费，字段用途不同：

| 路径 | 触发者 | 关键字段 | 说明 |
|------|--------|---------|------|
| 原生模式（DSL） | 填表 AI | Note + Init/Insert/Update/Delete | 纯文本提示词，无 SQL 执行 |
| SQLite 模式 | SQL 执行器 | DDL + Note + 四段触发 | DDL 定义物理结构，触发段生成 SQL |
| AI 改表助手 | visualizer 面板 | 结构化 `operations` 协议 | 只改配置/表头/内容/DDL，不写 SQL |

同一张表的 Note 和四段触发在三条路径间尽量一致，AI 才不会被互相矛盾的描述误导。

## 二、必须契约（不满足就失败或被拒绝）

以下规则由代码强制，违反时建表/保存会失败，或被安全门禁拒绝写入。**这不是建议，是契约。**

### 2.1 表名与身份

- 表名非空；同一聊天内表名不重复（重名会被拒绝）。
- 表的 `sheetKey` 由系统生成，不要手写或猜测。
- 表头（content 第一行）列名必须唯一；`row_id` 是首列固定身份列，不要改它的名字。

### 2.2 DDL 与表头映射（SQLite 模式）

- 第一列必须是 `row_id INTEGER PRIMARY KEY`。
- 表名用英文小写 + 下划线；不要用中文物理表名。
- 中文显示表头必须与 DDL 列一一对应，通过 `-- 中文列名` 注释声明映射；
  没有注释的列无法与 content 表头对应，建表校验会失败。
- DDL 列数必须与 content 表头列数一致（不一致时投影校验拒绝）。

### 2.3 删除、类型转换、物理迁移必须显式确认

- 删除列、类型转换、物理列迁移（改物理列名/类型）必须通过 `migrationIntent` 显式声明，
  并确认破坏性/有损转换；没有确认时门禁拒绝写入，不做模糊匹配。
- 单行表（如全局状态、主角信息）不允许 INSERT；Insert 触发写「禁止操作」，否则 AI 会反复插行。

### 2.4 AI 改表助手协议边界

- 输出必须是合法 draft JSON：`protocolVersion=2`、`mode="modify_current_template_incremental"`、
  `atomic=true`、含 `requestId/baseFingerprint/selectedSheetKey`、`warnings` 为字符串数组。
- 操作名只能在白名单内（见第六节对照表），`op` 字段是唯一操作名，禁止用 `type/operation/action` 别名。
- 涉及未知表、未知列、删除、类型转换、物理迁移、row_id 或 DDL 不一致时，不得猜测，
  返回 `warnings` 说明 + `operations=[]`。

## 三、推荐项（让 AI 更可靠，但不是强制）

以下不是代码契约，但强烈建议：填得越清楚，AI 的误操作越少。

### 3.1 表名

用名词短语，结尾加「表」字：`重要角色表`、`背包物品表`。
不要用动词（「打怪表」）或形容词（「酷炫的表」）。

### 3.2 Note：一行代表什么 + 逐列说明

- 第一段一句话说清这张表记什么、一行代表什么。
- 单行表写明「此表有且仅有一行」——这是防止 AI 乱 INSERT 的关键提示。
- 逐列说明格式：`- 列N: 列名 - 含义（+ 可选取值范围/约定）`。
- 有枚举值的列在括号里列出所有可选值；有字数/长度限制的列写明上限；
  存多值的列声明分隔符（如「用分号分隔」）。

### 3.3 四段触发：条件要精确

- Init：`<时机>，<做什么>。` 单行表必须初始化（唯一写入机会）。
- Insert：写明**什么情况插入、什么情况不插入**（「未记录」「全新」这类排除词有效）。
- Update：写明**什么情况更新、什么情况不更新**；多行表用业务主键定位，单行表用 `WHERE row_id = 1`。
- Delete：写明**什么情况删除、什么情况不删除**（「临时失守不删除」这类显式排除有效）。

### 3.4 单行表 vs 多行表

| 性质 | 多行表 | 单行表 |
|------|--------|--------|
| 业务主键 | 必填，加 `UNIQUE` | 不需要，用 `row_id = 1` |
| Insert | 写明插入条件 + SQL 示例 | 写「禁止操作」 |
| Delete | 写明销毁条件 | 写「禁止删除」 |

## 四、高级能力（可选，按需使用）

以下能力需要时再用，不需要不要硬加——加得越多，模型噪声越大。

- **约束**：`NOT NULL`、`UNIQUE`、`DEFAULT`、`CHECK`。业务主键加 `UNIQUE`；枚举加 `CHECK IN (...)`；
  数值范围用 `CHECK(x >= 低 AND x <= 高)`。
- **SQL 示例**：在触发段里给一条带 `WHERE` 的示例，AI 会照抄格式。
  注意：SQL 示例只在 SQLite 模式被消费，原生模式用不到。
- **长度/格式**：`CHECK(LENGTH(col) <= 20)`、时间格式 `CHECK(cur_time GLOB '????-??-?? ??:??')`。
- **复合/批量更新**：`quantity = quantity + 3`（加减表达变化）、批量 `WHERE quantity <= 0`。
- **触发器**：仅在你确实需要 SQLite 触发器时才写，且必须提供完整、可解析的 SQL；
  这不是每个表的必需品。

## 五、最小可用表（照抄即可）

只填三样东西就能用：表名 + 3~4 个表头 + 简短 Note。不需要 DDL、不需要 SQL 示例。

### 原生模式最小示例

```
表名：好感度表
表头：角色名 | 好感度 | 备注
Note：记录各角色对主角的好感度，一行一个角色。
  - 列0: 角色名 - 角色名称，唯一。
  - 列1: 好感度 - 数值，越高越友好。
  - 列2: 备注 - 补充说明。
Insert：剧情中出现未记录的角色互动时添加。
Update：好感度变化时更新，用加减表达变化幅度。
Delete：禁止删除。
```

### SQLite 模式最小示例（含 DDL）

```sql
CREATE TABLE favorability ( -- 好感度表
  row_id INTEGER PRIMARY KEY, -- 行号
  character_name TEXT NOT NULL UNIQUE, -- 角色名
  favor_level INTEGER NOT NULL DEFAULT 0, -- 好感度
  remark TEXT -- 备注
);
```

```
-- Note: 记录各角色对主角的好感度，一行一个角色。
-- 列0: 角色名 - 角色名称，唯一。
-- 列1: 好感度 - 数值，越高越友好。
-- 列2: 备注 - 补充说明。
-- INSERT: 剧情中出现未记录的角色互动时添加。
-- UPDATE: 好感度变化时更新，用加减表达变化幅度。
-- DELETE: 禁止删除。
```

> 不需要在每一段都写 SQL 示例。触发条件写清楚，AI 也能正确生成 SQL；
> SQL 示例是「让它照抄格式」的加强手段，不是必填项。

## 六、AI 改表助手的操作对照表

改表助手用结构化 `operations` 协议，而不是 SQL。按需求选一个操作：

| 你想做什么 | 用哪个操作 | 示例（片段） |
|-----------|-----------|-------------|
| 只改更新频率/上下文/批处理 | `patch_sheet_update_config` | `{"op":"patch_sheet_update_config","sheetKey":"sheet_xxx","patch":{"updateFrequency":60}}` |
| 只改 Note/Init/Insert/Update/Delete 说明 | `patch_sheet_source_data` | `{"op":"patch_sheet_source_data","sheetKey":"sheet_xxx","patch":{"note":"新说明"}}` |
| 改单元格/行数据 | `patch_sheet_content` | `{"op":"patch_sheet_content","sheetKey":"sheet_xxx","patch":{"updateCells":[{"rowNumber":2,"columnName":"好感度","value":"80"}]}}` |
| 只改中文显示表头 | `patch_sheet_schema`（`renameColumns`） | `{"op":"patch_sheet_schema","sheetKey":"sheet_xxx","patch":{"renameColumns":[{"from":"旧列名","to":"新列名"}]}}` |
| 增/删列 | `patch_sheet_schema`（`addColumns`/`deleteColumns`） | `{"op":"patch_sheet_schema","sheetKey":"sheet_xxx","patch":{"addColumns":[{"name":"新列","defaultValue":""}]}}` |
| 显式写 DDL | `patch_sheet_schema`（`patch.ddl`） | 仅在明确要求字段类型/约束/SQLite 建表语句时使用 |
| 物理列迁移/类型转换 | `patch_sheet_schema`（`migrationIntent`） | 必须完整提供 physicalColumnMappings/fills/conversions/migrationPolicy |
| 锁行/列/单元格 | `patch_sheet_locks` | `{"op":"patch_sheet_locks","sheetKey":"sheet_xxx","patch":{"rows":[{"rowNumber":1,"locked":true}]}}` |
| 全局注入配置 | `patch_global_injection_config` | 调整可读条目/包裹位置 |

**要点**：

- 只改更新频率时，**不要**顺带输出 `updateNode`、`headers`、DDL 或 content patch——那会把低风险请求变成跨层误操作。
- 只改显示表头时用 `renameColumns`，**不要**输出 `headers` 字段；本地会自动同步既有 DDL 注释。
- 同时改表头与 Note 时，输出两个独立 operation（一个 schema.renameColumns + 一个 source_data.note）。
- 物理列名迁移与显示名改名是两件事：只有明确要求物理迁移才输出 `migrationIntent`。
- 需求信息不足时，返回 `warnings` 说明 + `operations=[]`，不要输出追问文本。

## 七、常见坑与排雷

### 坑1：DDL 注释中文与 Note 列名不一致

DDL 注释的中文 = Note 里的列名 = content 表头，三者必须完全一致，否则 AI 张冠李戴。

### 坑2：多行表忘了加 `UNIQUE`

业务主键列（物品名/角色名/据点名）必须加 `NOT NULL UNIQUE`，否则 AI 反复 INSERT 同一实体。

### 坑3：单行表 Insert 写了 SQL 示例

单行表的 Insert 只写「禁止操作」。给了示例，AI 就会照抄 INSERT，单行表变成多行。

### 坑4：Update 示例没带 WHERE

所有 UPDATE/DELETE 示例必须带 `WHERE`。单行表用 `WHERE row_id = 1`，多行表用 `WHERE <业务主键> = 'xxx'`。

### 坑5：枚举列没写 CHECK 约束

Note 里列了枚举值但 DDL 没约束，AI 会自创值。Note 与 DDL 双保险：Note 列出枚举，DDL 加 `CHECK IN (...)`。

### 坑6：中文物理列名 / 无注释 DDL

中文物理列名、没有 `-- 中文列名` 注释的 DDL 会被校验拒绝（见 2.2）。

### 坑7：删除/类型转换无确认

删除列、类型转换、物理迁移没有 `migrationIntent` 确认会被门禁拒绝（见 2.3）。

## 八、保存前检查与失败后定位

### 保存前检查

- [ ] 表名非空、不重名。
- [ ] 表头唯一，`row_id` 在首列。
- [ ] SQLite 模式：DDL 列数 = 表头列数，首列 `row_id INTEGER PRIMARY KEY`，中文列名有注释映射。
- [ ] 单行表：Insert 写「禁止操作」；Delete 写「禁止删除」。
- [ ] 删除/类型转换/物理迁移：已显式确认。
- [ ] AI 改表助手：知道目标表、目标列、操作类型。

### 失败后定位（按阶段）

| 现象 | 阶段 | 检查什么 |
|------|------|---------|
| 建表校验失败 | 结构校验 | 表头唯一性、DDL 列数、注释映射、row_id |
| 保存被降级预检阻止 | 保存链路 | 聊天是否残留旧回放根（真实数据/后缀 artifact）；与「仅改配置」无关时才是结构差异 |
| AI 返回空 operations | AI 生成 | 需求是否明确要求修改；是 → 重新生成；否（检查用）→ 正常 |
| AI 输出非法 draft | 协议解析 | 顶层键、op 白名单、占位符是否保留 |
| 环境失败（SQLite 引擎不可用） | 环境 | 重试无意义，先恢复运行环境 |
| 迁移被拒绝 | 数据迁移 | `migrationIntent` 是否完整、破坏性/有损是否确认 |
